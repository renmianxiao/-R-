# 游集（PlayShelf）后台管理设计

- 日期：2026-10-01
- 状态：设计已由用户确认，等待书面审阅
- 项目：现有 React + Node 游戏商城

## 目标

为游集增加真实可操作的后台管理子系统，作为作品集展示前后端完整交付能力。后台第一阶段覆盖经营概览、商品管理、订单查看和订单状态更新。后台商品修改必须写入服务端数据，刷新商城后可见；订单状态也须持久保存。

## 已确认范围

### 包含

- `/admin` 管理入口及管理员身份识别。
- 经营概览：在售商品数、订单数、待处理订单数、演示订单金额。
- 商品列表、搜索、分类筛选、分页、新建、编辑、上架与下架。
- 订单列表、查看详情及状态更新。
- 服务端管理员权限校验、字段与状态校验、错误反馈和持久化。
- 本机管理员账号提权命令。

### 暂不包含

- 用户列表、封禁或用户角色管理页面。
- 真实支付、真实发货、优惠券、库存、报表导出。
- 图片文件上传；商品封面通过图片链接维护。
- 数据库迁移。此阶段使用项目现有 Node 服务和 JSON 文件存储，适用于本地作品集演示和低并发使用。

## 现状与约束

项目已有 React 19 前端、原生 Node HTTP API、注册登录、HttpOnly 会话 Cookie、演示订单及 108 款静态商品目录。注册账号当前没有角色字段；商品目录由 `data/catalog.mjs` 与 `data/ode-games.mjs` 提供；订单保存在 `data/orders.json`，订单状态初始值为 `demo-created`。项目没有 Git 仓库。

复用现有技术栈和登录会话，不引入数据库或额外运行时依赖。现有用户、会话及订单文件已由 `.gitignore` 排除，后续持久化商品文件也应避免纳入版本控制。

## 页面与交互

### 管理框架

`/admin` 使用独立管理布局，含侧边导航：经营概览、商品管理、订单管理，以及返回商城/退出登录入口。视觉沿用商城的深色背景和黄绿色强调色，表格、辅助文字和数字区域保证清晰对比。窄屏下表格允许横向浏览。

非管理员打开管理入口时显示无权限提示和返回商城操作。界面门禁仅负责用户体验；所有管理 API 必须再次在服务端检查管理员身份。

### 经营概览

- 在售商品数。
- 全部演示订单数。
- 待处理订单数（状态 `demo-created`）。
- 演示订单金额（排除已取消订单，不代表真实营收）。

### 商品管理

表格展示封面、商品名称、分类、现价、原价、评分、销售状态和操作。支持关键词搜索、分类筛选及分页。表单允许新增和修改商品目录已有的字段：商品名、英文名、分类、标签、售价、原价、评分、封面链接、展示颜色、短描述、商店应用 ID 和推荐标记。服务端验证必要文本长度、数字范围、图片链接格式和商品 ID 唯一性。

存量目录首次初始化为全部在售。下架以 `active: false` 保存，不物理删除商品；上架设置为 `active: true`。商店 API 只返回在售商品。订单行仍使用创建订单时保存的商品名、数量和单价快照，不随商品后续修改而变化。

### 订单管理

订单列表展示订单号、创建时间、联系邮箱、商品摘要、金额和状态；可按订单号/邮箱搜索、按状态筛选并打开详情。界面将既有 `demo-created` 显示为“待处理”。可变状态限定为 `demo-created`、`processing`、`completed`、`cancelled`，分别显示为“待处理”“处理中”“已完成”“已取消”。状态更新记录更新时间和操作者。取消订单需要确认。所有页面文案明确这只是演示订单，不存在真实付款或履约。

## 权限与账号引导

所有新注册账号服务端默认角色为 `customer`，注册请求忽略或拒绝用户自行提交的管理员角色。管理员通过本机命令 `npm run admin:promote -- <邮箱>` 从已注册用户中指定；命令只修改本地 `data/users.json` 中匹配账号的角色，不输出密码或会话令牌。命令应在用户不存在时给出清晰错误。

会话验证仍使用现有 HttpOnly Cookie。登录用户信息向前端提供非敏感角色字段，供路由展示判断；每个 `/api/admin/*` 处理器仍通过当前有效会话重新读取角色，并对未登录和非管理员请求分别返回未认证/无权限响应。写请求保留同源与 SameSite 保护，不开放跨域管理访问。

## 后端结构与数据流

- `data/games.json`：第一次读取时由现有静态目录初始化，之后作为商品管理的持久化数据源。
- `data/orders.json`：继续保存现有订单结构；后台只更新状态与审计字段。
- 用户记录新增角色，普通用户默认为 `customer`，管理员为 `admin`。
- `GET /api/games` 从持久化商品读取并仅返回在售商品。
- `POST /api/orders` 使用同一商品数据源，只接受仍在售的商品，并以服务端当前价格生成订单行快照；客户端提交的价格不作为依据。
- `/api/admin/overview`、`/api/admin/games`、`/api/admin/orders` 及其写操作由管理员保护的 API 提供。
- 商品/订单写入先校验，再写入临时文件并原子替换；单进程内串行化文件更新，避免并发请求互相覆盖。
- API 使用 400 表示无效输入、401 表示未登录、403 表示非管理员、404 表示记录不存在；服务端故障以可理解的中文错误响应，前端展示重试或修正提示。

## 组件边界

- 管理页面壳层负责加载管理员身份、导航和无权限状态。
- 概览页只读取聚合数据，不自行重算持久化值。
- 商品页与订单页分别管理表格、筛选、分页、编辑/详情交互，通过共享 API 客户端请求数据。
- Node 管理路由负责授权、验证和调用文件存储逻辑；文件存储逻辑不负责 UI 规则。

## 验收标准

1. 新注册账号为普通用户，不能通过提交注册字段获得管理员权限。
2. 本机提权后，管理员可登录并进入 `/admin`；普通用户直接访问页面和管理 API 均被拒绝。
3. 新建、编辑及下架商品后，刷新商城 API/页面能看到对应结果；下架商品不出现在商城。
4. 修改商品不会改变已存在订单中的商品名和下单单价。
5. 管理员更新订单状态后刷新页面仍保留，非法状态更新会被服务端拒绝。
6. 空数据、加载失败、无权限、表单验证失败等状态均有清晰反馈。
7. 现有注册、登录、购物袋和演示下单流程继续工作，生产构建成功。

## 风险与限制

JSON 文件存储适用于本地演示和低并发；多进程部署、跨实例写入、生产级审计与备份需要数据库和更完整的运行配置，属于后续阶段。管理员提权命令需要能访问本机项目数据目录。演示订单金额不应作为真实销售指标展示。
